Reports with a desktop-app feel, in the browser

Design for sign-off · 2026-11-03 · builds on docs/REPORTS_APP_PLAN_2026_11_03.html (the Reports app on its own pod) · nothing is built yet

In one paragraph. Finance users want their reports to feel like a program on their PC: an icon in the Start menu, a window of its own, instant sorting and drilling, and a report that still opens when the network is slow or gone. They do not want another Excel. Power BI gets this by shipping a separate desktop program. We do not need one: a modern browser (Edge, Chrome) can install a web app onto the PC and can run a real database engine inside the page (WebAssembly). The recommendation is in two steps. Step one makes the Reports app installable (icon, own window, loads instantly) — small, safe, a few days. Step two lets a person take a local copy of a report they have already run, holding only the rows they are allowed to see, and drill, filter, pivot and sort it on their own machine with no server round trip — online or offline — under a lease the server can end at any time. A separate desktop program (Electron / Tauri) is not recommended, and a double-clickable report file is a later, optional step. Every phase ends with a Docker rig proof and a browser walk.

1 · What "desktop-like" can mean here, and what users actually need

"Like a desktop app" is six different wishes. Each is listed with what the user feels, whether a finance user needs it, and how it can be had.

What Power BI really does. Power BI has a web service (where people read reports) and a desktop program (where analysts build them). The reading experience that finance users like — fast cross-filtering, drill, slicers — comes from a data model loaded into memory. In the web service that model sits on Microsoft's servers; in the desktop program it sits on the PC. The design here gives our readers the second feeling (a model on the PC) without a separate program, and keeps the first (server runs, row security) as the source of truth.

3 · The WebAssembly option, concretely

In plain words. WebAssembly lets a browser run real compiled programs at near-native speed. DuckDB — the database engine our server already uses to drill a stored result — is published as such a program (DuckDB-WASM). Loaded into the page, it can read the same result file the server reads and answer the same questions, on the user's own PC, in milliseconds, with no server call. The server still runs the report (that is where the data and the row security are); the browser only works on the finished, already-filtered result it was given.

3.1 What a user would do

  1. Open a report as today. It runs on the server; the result is stored and row-secured for that person.
  2. Click Work on this computer (shown only when the result is within the size cap). The app downloads the result once and keeps it in the browser's private storage, encrypted.
  3. From now on, every click on that report — sort, filter, drill, open an outline row, change a slicer, a linked tile — is answered on the PC. A small chip says "On this computer · as of 09:12 · expires in 6 days".
  4. Offline, the installed app still opens the report and every tile works. Running it again, changing a parameter, exporting Excel/PDF, commenting, signing off, sharing — these need the server and say so.
  5. When the lease ends, or an admin revokes it, or the person loses access, the copy is deleted and the app goes back to the server.

3.2 How big a result can this hold?

The honest answer is "far more than today's in-browser engine, far less than the server".

  • Today's browser engine holds JavaScript objects: ~2 KB per row, measured; 50,000 rows is the configured ceiling; 250–300k rows crashes the tab.
  • DuckDB-WASM holds columnar data (parquet / Arrow): a 30-column mostly-numeric row is roughly 150–300 bytes in memory. 1,000,000 rows ≈ 150–300 MB — comfortable. 5,000,000 rows ≈ 1–1.5 GB — near the edge of what a tab is allowed.
  • The hard ceilings: WebAssembly addresses at most 4 GB, and browsers impose stricter per-tab limits; DuckDB-WASM runs on a single thread by default (multithreading is still marked experimental and needs cross-origin isolation headers, which would break the embedded-report iframes and the Office add-in — so: single thread).

Proposed cap (a cap throttles, it never refuses the server road): a new setting business_reports.local_copy_max_rows, default 1,000,000 rows, and local_copy_max_bytes, default 300 MB of result file. Above either, "Work on this computer" is not offered and the sentence says why; the server cube stays as today. The default is set after the Phase 1 measurement on the rig (the owner's 1M-row month-end JOIN, 54 columns, is the test case), not guessed.

3.3 How the copy is loaded and kept

  • Bytes. A new signed-in route GET /api/business-reports/{id}/results/{exec_id}/local-copy streams the result as Arrow IPC (the store already builds Arrow IPC from the parquet: core/artifacts/store.py::build_arrow_ipc_from_parquet) or parquet, with the schema's column names replaced by the report's own column labels (a packer, new, reusing the redaction list). Exact DECIMAL columns stay DECIMAL in parquet (the microcube's "added up AS ITSELF" rule holds locally; Arrow float64 is only for drawing).
  • Storage. The file lands in the Origin Private File System (OPFS): a per-site private directory, fast, up to the browser's per-origin quota (hundreds of MB to several GB, dynamic). The browser can evict it under disk pressure or long inactivity and a user can clear it in site settings — so it is a cache, never the only copy of anything. navigator.storage.persist() is requested for the installed app.
  • Engine. DuckDB-WASM (npm @duckdb/duckdb-wasm, MIT; stable 2.0.0 per the DuckDB docs; the OPFS persistence post of 2026-09-18 tested 1.32.0 and advises pinning a tested version) runs in a Web Worker, so the page never freezes. The engine bundle (~5–10 MB of wasm) is a hashed asset served by spa-server.cjs, loaded lazily the first time a copy is opened, and cached by the service worker thereafter. It is never fetched from a public CDN (the rig is offline; production is behind the firewall).
  • Opening. The decrypted bytes are registered with the engine (registerFileBuffer for a file held in memory, or the engine's own opfs:// handling for a persisted DuckDB database); a view is created over it; every tile's cube body is translated to SQL by localCube.ts (new) — a line-for-line sibling of microcube.py::read_artifact_drill / _build_where / _any_of_clause / _order_clause / _limit_clause, with the same grain gate (measure_eligibility) and the same prepared-statement values.
  • The seam. CanvasTileView, CanvasOutlineTile, the band, the report table page and the linked tiles already go through one fetcher (api.queryReportCube / queryReportCubeFast / the paged results). A CubeSource context (new) decides per report: server (today) or local (the worker). Insight tiles stay on the server (they need the server's stories and diagnostics).
  • Streaming. The first open can begin while the file downloads (Arrow IPC is batch-wise; the store already serves ranges); the chip says "Loading 40%". A result above the cap never starts.

3.4 What stays on the server — always

  • Running the report: SQL, connections, parameters, the row-security rewrite, the value lists, "latest date with data", schedules and subscriptions.
  • Deciding who may see what: the capability check, the row-security signature, grants, switched-off reports.
  • Excel and PDF exports with the canvas layout; share links and embeds (server cube only); comments and sign-off; the Download Centre; usage and audit.
  • The copy's lease: its expiry, its revocation, and the key that unlocks it (section 4).

4 · Security first

A local copy is a new place where report data lives. Each question below has one answer and one mechanism.

Recommendation

  1. Make the Reports app (the new entry from the Reports app plan) an installable PWA now: icon, own window, instant open. Also offer "Install" in the QueryStudio app for installations that do not deploy the Reports app.
  2. Build the local copy on DuckDB-WASM for signed-in readers, under a lease the server can end, encrypted at rest, audited in the Download Centre, capped by size, with the server cube as the road that always works.
  3. Hold the local engine to the server's numbers with the same parity gate that holds today's browser engine (goldens through the real route, by value, mutation-checked).
  4. Do not build a desktop program. Revisit only if a customer requires macOS file associations or a locked-down kiosk.
  5. Keep the .qsr file as an option for later; it adds a metaphor, not a capability.

7 · Limits, stated plainly

  • Browsers. Install to the Start menu and file handlers are Edge and Chrome on Windows (and Chrome on macOS/Linux). Firefox does not install PWAs on desktop; Safari installs to the Dock from macOS Sonoma but has no file handlers. OPFS and WebAssembly are in every current browser. The design assumes Edge or Chrome on the finance desktop; everything degrades to "the web page as today".
  • Memory. WebAssembly addresses at most 4 GB and browsers allow less per tab; the cap in section 3.2 keeps copies well inside it. A report above the cap has no local copy and says so; it is never cut.
  • One thread. DuckDB-WASM multithreading is experimental and needs cross-origin isolation, which would break embedded reports and the Office add-in. Single-threaded local drills on 1M rows are still expected in the tens to low hundreds of milliseconds; Phase 1 measures it.
  • Storage is a cache. The browser may evict OPFS under disk pressure or after long inactivity; clearing site data deletes it. The copy is always re-makeable from the server while the lease is valid.
  • Offline revocation is bounded by the lease, not instant. Section 4 says this twice on purpose. The per-report "short lease" and "never" settings are the control.
  • Bundle size. The engine adds several MB of wasm, loaded only when a copy is first opened and cached by the service worker afterwards. The first open on a slow link is slower than today; every later open is faster.
  • Corporate policy. Some IT policies block PWA installation; the same policies can push it (Intune / Edge WebAppInstallForceList). Nothing here needs admin rights on the PC.
  • Licensing. DuckDB and DuckDB-WASM: MIT. Apache Arrow (not needed; our reader is our own): Apache 2.0. Workbox, if used for the service worker: MIT (a hand-written worker of ~100 lines needs no library). Electron: MIT; Tauri: MIT/Apache 2.0 — moot under the recommendation. No licence cost in any option.
  • Versions move. DuckDB-WASM's OPFS support was tested by DuckDB on 1.32.0 (2026-09) while the docs name 2.0.0 as stable; the Phase 1 spike pins one tested version and the dependency guard keeps it pinned.

8 · Decisions for you

Each has my recommendation. "Go" takes them all.

  1. Scope of the installable app: the Reports app only, or QueryStudio too? Recommended: both entries get the manifest; the Reports app is installed by default, QueryStudio offers the button.
  2. Build the local copy (option B) at all? Recommended: yes; it is the only option that gives "Excel desktop features" without Excel.
  3. Default local-copy policy per report: allowed with a 7-day lease, a short lease (8 hours), or off until an owner turns it on? Recommended: allowed, 7 days, matching downloads retention; a report owner may set short or never; an admin may set the installation default.
  4. Who may take a local copy: every viewer, or analysts and above? Recommended: every role that may view the report (the capability reports.local_copy seeded on), because the viewer is exactly the finance reader this is for.
  5. Size cap defaults (1M rows / 300 MB proposed) — confirm after the Phase 1 measurement, or set now? Recommended: set after measurement on the month-end JOIN.
  6. The .qsr file (phase 3): build it, or stop after keyboard and windows? Recommended: not now; add it if users ask for "a file I can open", after they have used the local copy.
  7. Electron / Tauri: confirm not building a desktop program. Recommended: confirm.
