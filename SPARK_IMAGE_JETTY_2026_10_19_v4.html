Building a Spark image that passes the Jetty scan

2026-10-18 · for whoever builds QueryStudio's Spark job image. CVE-2026-2332 (jetty-io / jetty-http) and CVE-2026-10050 (jetty-security) are both rated critical, and they block the image scan. Every version below was measured by scanning the jars inside the real images on 2026-10-18 (§7). Nothing here is taken from release notes alone.

0 · The tested recipe (2026-10-19): follow this

Every step below was run on Docker. Each one exists because leaving it out broke a real run (see §11). The reference Dockerfile is spark/Dockerfile.spark42 in the QueryStudio repo (branch feature/2026-10-18-spark42-jetty).

  1. Build Spark 4.2.0 from source with Jetty 12.1.14. The build machine needs Java 21, Maven, git, python3 and zip; without zip the packaging step fails at the very end. 
    git clone --branch v4.2.0 --depth 1 https://github.com/apache/spark.git && cd spark
./dev/make-distribution.sh --name qs-jetty12114 --tgz \
    -Pkubernetes -Phadoop-cloud -Phive -Phive-thriftserver \
    -Djetty.version=12.1.14 -DskipTests
# -> spark-4.2.0-bin-qs-jetty12114.tgz  (~1 GB; about 30 min with a warm Maven cache)
    -Phive -Phive-thriftserver are required. The official images are built with them, and without them the job's Iceberg catalog fails with NoClassDefFoundError: org/apache/hadoop/hive/metastore/api/NoSuchObjectException.
  2. Build the job image from that tarball with spark/Dockerfile.spark42 (save the tarball as spark/spark-dist.tgz): 
    cd spark && docker build -f Dockerfile.spark42 -t <registry>/querystudio/spark-etl:<tag> .
    It starts from the official apache/spark:4.2.0-scala2.13-java21-python3-ubuntu image (OS, Java 21, Python, entrypoint, user 185) and replaces its jars/ and python/ with the rebuilt ones. Then it adds:
    • the JDBC drivers, with trino-jdbc 484 (455 fails on 4.2);
    • analyticsaccelerator-s3 1.3.1 (s3a needs it on Hadoop 3.5);
    • Iceberg 1.13 for Spark 4.2 (step 5);
    • the job code.
    It also removes Hadoop's Jetty, using spark/scripts/strip_hadoop_jetty.py.
  3. Remove ONLY Hadoop's Jetty, never spark-core's (§1b: Spark cannot start without it).
  4. Check the image: scripts/spark_image_jetty_scan.py inside it must exit 0 with 0 Jetty artifact(s) older than 12.1.10. Then run your scanner or Trivy.
  5. Iceberg: no RELEASED Iceberg build exists for Spark 4.2. The 4.1 build (1.12.0) FAILS on 4.2. The nightly 1.13.0-SNAPSHOT passed every test, but a snapshot is not for production. Use the Iceberg 1.13.0 release when it is published, by changing the two ICEBERG_* build arguments at the top of the Dockerfile, and re-run §9.
  6. QueryStudio's job must be the version on that branch. On Spark 4.2 Iceberg refuses the reader option snapshot-id. On Spark 3.5 the replacement, versionAsOf, is silently IGNORED (it read the latest data instead of the pinned snapshot). The job now picks the option by Spark version (generic_feed._iceberg_pin_option). That is proven on 3.5 (all pod tests green) and on 4.2.
  7. Give the driver at least 2 GB (spark_k8s.driver_memory). On the same 1 GB driver, Spark 3.5 passed and Spark 4.2 was OOMKilled delivering ~18M rows; with 2 GB, 10/10.
  8. Never use spark-core without its Jetty, and never spark.ui.enabled=false as a "fix": neither keeps Spark running without Jetty (§1b).

1 · The answer in short

  • Spark must be 4.2.x. It is the only Spark line on Jetty 12. Jetty 9.4, 10 and 11 are end-of-life, and CVE-2026-10050 will not be fixed on them.
  • Even Spark 4.2.0 is not enough as shipped. It carries Jetty 12.1.8, but CVE-2026-10050 needs 12.1.10 or later. Build Spark 4.2.0 with a newer Jetty (§4); 12.1.14 is the latest release.
  • Hadoop's built-in Jetty 9.4 must be removed (§5). Every released Hadoop, 3.5.0 included, still bundles Jetty 9.4, so no Hadoop version clears it.
  • Iceberg is the open risk (§6). QueryStudio's Spark pods read Iceberg tables, and no Iceberg build exists for Spark 4.2 yet. The 4.1 build has to be proven on 4.2 before the image ships.

1b · Do NOT strip Jetty from spark-core: the scan passes and Spark never starts

Tested on Docker (2026-10-18), with apache/spark:4.1.2 and every Jetty class and pom removed from spark-core and hadoop-client-runtime:

  • The jar scan reports 0 Jetty, and so does an image scanner.
  • But every Spark job fails at start-up with java.lang.NoClassDefFoundError: [Lorg/sparkproject/jetty/servlet/ServletContextHandler;, thrown at org.apache.spark.metrics.MetricsSystem.getServletHandlers from SparkContext.<init>.
  • The setting does not help: it fails the same with spark.ui.enabled=false, with the UI on, and with the metrics servlet sink switched off.
  • The identical job on the unstripped image wrote and read 1,000,000 rows on S3 with the sum exact. The strip is the only difference.

Spark's own Jetty must be REPLACED (12.1.10+, which means Spark 4.2, §4), never removed. Hadoop's copy can be removed (§5): proven, because Spark does not load it.

The rule: every Jetty copy in the image must be 12.1.10 or later, or gone.

3 · Where Jetty is: inside two jars, never on its own

No jetty-*.jar sits in /opt/spark/jars. Jetty is shaded (copied and renamed) inside two jars, and scanners find it through the Maven pom.properties files those jars carry.

4 · Spark's Jetty: build Spark 4.2.0 from source with Jetty 12.1.14

Spark's build takes the Jetty version as a property. 12.1.8 → 12.1.14 is a patch upgrade on the same line, so the Spark code is unchanged.

git clone --branch v4.2.0 --depth 1 https://github.com/apache/spark.git
cd spark
./dev/make-distribution.sh --name qs-jetty12114 --tgz \
    -Pkubernetes -Phadoop-cloud -Phive -Phive-thriftserver \
    -Djetty.version=12.1.14 -DskipTests
# needs zip on the build machine; -Phive is REQUIRED (see §0)
# then build the job image with spark/Dockerfile.spark42 (§0 step 2)

Corrected 2026-10-19: the first version of this command lacked -Phive -Phive-thriftserver and did not mention zip. Both broke a real build or run.

Use Java 21; the official 4.2.0 image runs OpenJDK 21. Python in the official 4.2.0 Ubuntu image is 3.10.

5 · Hadoop's Jetty 9.4: remove it

QueryStudio's job uses Hadoop only as an S3 client (s3a, for the artifact store and S3 reads and writes). The Jetty inside hadoop-client-runtime serves Hadoop's own web servers (NameNode UI, KMS, WebHDFS), which a client never starts. There are two ways to remove it.

A. Delete the shaded Jetty from the jar at image build (smallest change):

cd /opt/spark/jars
zip -d hadoop-client-runtime-*.jar \
    'org/apache/hadoop/shaded/org/eclipse/jetty/*' \
    'META-INF/maven/org.eclipse.jetty*'
# run §7 afterwards: it must list no Jetty in hadoop-client-runtime

B. Build Spark with -Phadoop-provided, then add the plain Hadoop jars yourself (hadoop-common, hadoop-aws, the AWS SDK v2 bundle), leaving out every jetty-* jar.

Either way, prove S3 still works before shipping: a feed that writes its file through s3a and a feed that reads S3 on a Spark pod (QueryStudio's Docker Spark rig does both).

7 · Check the image before the scanner does

Jetty copies, per jar, with versions: scripts/spark_image_jetty_scan.py (in the QueryStudio repo, and beside this page in qsd). It exits 1 if any Jetty older than 12.1.10 is present.

docker run --rm -v "$PWD/scripts:/s:ro" --entrypoint python3 <your-image> /s/spark_image_jetty_scan.py

Measured output on today's image (exit 1):

    ...

Full CVE scan:

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image <your-image>

Target: the jar scan prints 0 Jetty artifact(s) older than 12.1.10 and exits 0, and Trivy shows no CVE-2026-2332 or CVE-2026-10050.

8 · The other two images with the same Jetty

  • The QueryStudio API image installs pyspark 3.5.3 (backend/requirements.txt) for the Spark Connect client. That package bundles the same spark-core and hadoop-client-runtime jars, so the same two CVEs are there. The fix is to replace it with pyspark-client 4.2.0: the Connect client only, pure Python with no Java jars, Python ≥ 3.10. That removes Jetty from the API image entirely. The API's two PySpark uses (the Spark Connect session and the Connect test route) work with it.
  • The Spark Connect server (k8s/spark-connect/, today apache/spark:3.5.3) has the same Jetty. The client and server must share a major version, so it moves to the same 4.2 image.

9 · Proof before it ships

Hand QueryStudio the new image name. On the Docker Spark rig, these must pass:

  1. feeds on Spark pods, every format and delivery;
  2. S3 reads, and writes through s3a;
  3. the Iceberg merge-on-read check (17,850 exact);
  4. the 40M-row and partition-by-key feeds, compared with native;
  5. Spark 4's stricter casting (ANSI mode is on by default in Spark 4). A cast that used to give NULL now fails, so check value by value;
  6. the jar scan and Trivy on all three images.

Airflow: no change. Every lane stays available until that decision is made.
