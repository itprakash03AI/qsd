Release 2026-08-19 — Ocean-Dive Visibility, Pod Roles, Dependency Truth & Starburst Parity Incident

29 commits f7f0a510 → b3a97650  ·  114 files, +9165/−662  ·  backend 16,438 passing  ·  ETL 3,247 passing / 0 failing

Triggered by a production incident: a user selected a single region (eu-west) and the query crashed — DuckDB query execution crashed (exit code 1, exit code 1) at memory_limit=3.4GB. The report was “the pruning brain is diving in oceans, not islands”. Three independent defects turned out to sit on one chain: the predicate was lost silently, the resulting full-table scan had no alarm on the parquet path, and the error message discarded the actual cause. A fourth, unrelated thread — three dependency manifests that had drifted from what the code imports — explained a second machine’s ~900 failing tests.

1. The error message discarded the error Diagnostics

The DuckDB child process catches the exception, sanitizes it, and writes {"error": "<Type>: <msg>"} to the same result file the parent reads on success — then exits 1. The parent’s returncode != 0 branch raised on the exit code alone and never opened that file. Every ordinary query failure — OOM, spill exhaustion, an httpfs 403/404, a corrupt parquet — therefore reached the operator as the engine’s boot banner with no cause. exit 1 was also the only common exit code with no decoder entry, producing the tautology.

The discipline behind every fix

Starburst / Trino Parity — the SQL we sent was not the SQL Trino accepts Correctness

commit 49a34668  ·  12 files  ·  54 new tests

A deep audit of the Trino/Starburst route found the parts everyone looks at were clean — LIMIT/0-unlimited semantics, the visual-filter compile chokepoint, Iceberg partition-DDL parsing — while the SQL actually put on the wire was not. Every defect below was reproduced live against the repo venv before being fixed, not inferred from reading. For a Starburst table the visual builder emitted: 

WHERE "business_close_date" = '2026-08-13'
  AND "event_ts" >= '2026-08-13T00:00:00.000000Z'
  AND "is_active" = 'true'
  AND "acct_num" = '007'
LIMIT 7 OFFSET 50

The first three are hard failures (Cannot apply operator: date = varchar(10)). The fourth is the dangerous one: against a varchar column storing unpadded account numbers it does not error — it matches nothing and returns HTTP 200.

1. The typed-literal machinery was unreachable Data loss

sql_literal has rendered DATE '…' since 2026-08-13, and the Published-View wrap and federation were both taught to pass a type. The visual route never was: FilterModel had no data_type field and render_inline called the one-argument sql_literal, so on that route the whole feature was dead code. Param now carries the type, compile_filter_condition stamps it once for all 13 operators (skipping contains/not_contains, whose parameter is a LIKE pattern and must stay a string), sql_literal learned boolean and numeric, and a new core/column_types.py resolves types from the catalog when the caller supplies none — cached, fail-open, with a caller-declared type always winning.

2. Pagination used the wrong grammar Fix

Trino, Starburst, Presto and Athena require OFFSET before LIMIT, and Oracle has no LIMIT keyword at all — while build_query_sql’s own docstring advertised its output as “suitable for any SQL connector”. Every paged visual query past page 1 failed on Starburst with a parse error. A new pagination_clause() is the single authority; 0 still means unlimited on every dialect.

3. The user’s SQL was rewritten for the wrong engine Wrong table

Both the BF-577 Starburst-compat cleanup and translate_to_duckdb_with_fixes ran before _conn_type was resolved (~400 lines later), so they rewrote blind. Raw Starburst SQL reached Starburst with date_parse() turned into STRPTIME() — not a Trino function — and catalog.schema.table stripped to a bare registered name, which on Trino resolves against the session catalog: a different table, read without error. Both are now gated on the target engine.

4. A filter that would not render silently vanished Data exposure

_build_condition returned None for an unknown operator or a half-supplied BETWEEN, and its comment called this “the safer fail-open”. It is not safe: dropping a filter does not degrade the answer, it widens it — more rows than the caller asked for, served as HTTP 200 on a published API. Worse, feed_engine caught the failure, logged “running unwrapped”, and delivered the unfiltered table to its SFTP / email / S3 destination as a successful run.

Unrenderable filters now raise; the feed aborts rather than delivering. A filter nobody supplied a value for is still skipped — that is an absent filter, not a broken one, and the split is what makes failing safe.

Row Security — two ways to serve rows a policy excludes Security

commit a3dae4f5  ·  15 new tests

1. Visual queries on SQL connectors had no row security at all

secure_sql was applied to raw SQL, and the DuckDB structured path secures a synthesized query inside execute_query_background — but SQL built by build_query_sql on the connector branch went straight to execute_sql_connector_background, which contains no row-security code whatsoever. The net effect: the same visual query was filtered against S3/parquet and unfiltered against Trino, Snowflake, Databricks, Oracle and Athena. It is now secured at the dispatch, fail-closed to 403 if policy resolution itself fails. Separately, every secure_sql call hardcoded dialect="duckdb"; the raw-SQL site now passes the target’s dialect so Trino SQL is not parsed and re-emitted through the wrong grammar.

2. The “fail-closed” fallback failed open

Six sites fabricate a principal when the real one cannot be resolved — an AD lookup that is down, a share token, a report with no recorded owner — as {role: "viewer", groups: []}. The scheduler documented it as: “That can only ever restrict further (drop rows), never leak extra rows.”

That is backwards in this engine. Policies are grant-shaped — bound to user: / role: / group: / all:* principals — and the rewriter leaves a table with no matching policy unfiltered. The groups are what carry the restriction, so dropping them removes it: 

policy bound to   group:emea-only  ->  region = 'EU'
    matches full ctx     : True
    matches stripped ctx : False        <- every region delivered

A fabricated context is now marked rls_unresolved, which lets the rewriter separate the two cases an empty policy list used to conflate: a table with no policies is not an RLS concern and still runs (the common case — refusing there would break every deployment that does not use RLS), while a table that has policies refuses. Telling them apart needs a principal-agnostic lookup, and that check itself fails closed, because “we could not check” is not “there is nothing to check”.

One subtlety decided the fix: the new error subclasses PolicyRewriteError, whose handler fail-opens. It is therefore caught first and re-raised as PolicyResolutionError, which every caller already turns into a hard 403 or a failed execution. A visible failed run replaces a silently wider one.

3. querystudio webserver is NOT API-only on its own Gotcha

The subcommand name promises exactly what you want, and it does something narrower. It sets QUERYSTUDIO_SCHEDULER_MODE=external — the legacy gate — which turns off three daemons: iceberg_metadata_sync, iceberg_manifest_watcher and brain_duckdb_mirror. Everything else still starts: prewarm, custom_jobs, the remaining mirrors, the Kafka consumer, the DQ scanner, agents, DataFlow, the SLA scanner, adaptive prefetch and the retention sweeps.

That gap is the whole reason QS_POD_ROLE exists — it was the 2026-07-02 finding that the API pod paid for the entire brain fleet despite scheduler.mode=external. None of the CLI subcommands expose a role flag (--host, --port and --workers are all they take), so set the env var alongside it. The env var wins over the legacy mode, so the combined form above does give you a genuine API-only process.

4. Why it cannot be a uvicorn flag

uvicorn main:app imports the module and looks up the app object. There is no channel for passing a value through an import, and uvicorn rejects options it does not recognise — its CLI accepts only its own. More decisively, --workers N makes uvicorn fork and re-import: each child re-runs module import from scratch, so environment variables are inherited but function arguments held in the parent are not. Any flag would have to end up in os.environ anyway to reach the workers, which is why the role was designed as an env var rather than a parameter.

One caveat if you use raw uvicorn instead of python main.py: you bypass run_server(), which sets WindowsSelectorEventLoopPolicy on Windows and wires SSL from server.ssl_certfile / ssl_keyfile. Neither usually matters for local API testing, but the event-loop policy is the one that occasionally bites on Windows.

Step 1 — Export the AD CA
# Grab the AD server cert chain and extract the CA cert
openssl s_client -showcerts -connect dc.company.com:636 </dev/null 2>/dev/null \
  | sed -ne '/-BEGIN CERT-/,/-END CERT-/p' > ad-ca.crt

# OR ask your PKI team for the corporate root CA PEM directly
Step 2 — Create the Secret
oc create secret generic ad-ca \
  --from-file=ca.crt=./ad-ca.crt \
  -n querystudio-prod
Step 3 — Enable in Helm
helm upgrade --install qs-api k8s/helm/querystudio-api/ \
  -f k8s/helm/querystudio-api/profiles/production/values.yaml \

Option A (dev/testing only): Skip the Secret and set "ad_tls_validate": false in config.json — bind succeeds without cert validation. Never use this in production.
FIPS / OpenShift gotcha: If ad_server is written as LDAPS:// (uppercase) or has stray whitespace, the case-insensitive normalisation (commit db66d72) still detects it — but older builds would silently fall through to NTLM, which triggers hashlib.new('md4', ...) → FIPS crash. AD login fails: "Bind failed — Authentication error" on OpenShift/FIPS ISSUE ▶
Root cause: NTLM bind calls hashlib.new('md4', ...). OpenSSL on OpenShift/FIPS rejects MD4 → bind crashes with a generic "Authentication error" (works fine locally where MD4 is allowed).
Diagnose — check the AD bind decision log

# Expected for LDAPS:
#   AD bind decision: ... normalized_url='ldaps://...' → use_ssl=True → auth_method=SIMPLE
# Bad (falls through to NTLM → MD4 → FIPS crash):
#   AD bind decision: ... use_ssl=False → auth_method=NTLM
Fix
1. Case-sensitivity: commit db66d72 normalises the URL with .strip().lower() so LDAPS:// / ldaps:// / trailing whitespace all route to SIMPLE bind.
2. Config: set "ad_server": "ldaps://dc.company.com" and "ad_use_ssl": true in config.json.
3. Force rollout: oc rollout restart deploy/querystudio-api -n <ns>.

AD login fails: "socket ssl wrapping error: certificate" (hostname mismatch) ISSUE ▶
Root cause: CA is correctly loaded, but the AD cert CN/SAN (e.g. dc01.INTRANET.corp.COM) doesn't match the hostname in ad_server (e.g. intranet.corp.com). Python auto-enables check_hostname=True when verify_mode=CERT_REQUIRED, rejecting the cert. May also cause a 22-second hang before failing.
Fix — disable hostname checking (default since commit dc6eb6c)
# In config.json → auth section — this is already the DEFAULT (false):
"ad_tls_check_hostname": false

# Verify in logs:
oc logs deploy/querystudio-api | grep "AD TLS:"
# Expected: AD TLS: validate=True  check_hostname=False  ca_file=/app/certs/ad-ca/ca.crt

# If you've upgraded to dc6eb6c or later, this is automatic.
# Only set ad_tls_check_hostname=true if your AD cert has SANs matching ad_server.
AD certs are almost always issued to a specific DC FQDN (e.g. dc01.intranet.corp.com) rather than the domain name used in ad_server (e.g. intranet.corp.com). The ad_tls_check_hostname config (default false) disables hostname verification while keeping cert chain validation (CERT_REQUIRED). The fix also applies connect_timeout to the SSL handshake itself, preventing 22-second hangs on cert errors.
