Setting up thousands of feeds from SQL

For the team setting up the month-end feeds (one feed per system entity and event, from the two shared queries). Works on QueryStudio's own PostgreSQL database.

1 · The idea in one paragraph

You describe a feed once, as a template with blanks ({SYSTEM_ENTITY}, {EventCode}). Then you give it a list of values. QueryStudio creates one feed per row of the list. Every feed gets the same checks as one made on screen: name rules, file-name clashes, dependency loops, password handling and version history. You do this with one SQL call, the way you would call a procedure in an Oracle package:

SELECT qs_feed_template_apply(...);   -- returns a request number
SELECT * FROM qs_feed_template_apply_status;   -- what happened

Within about 10 seconds QueryStudio picks the request up and applies it in the background, then writes the result into the status view.

2 · Why not insert into the feed tables directly?

An INSERT into feed_configs skips every check above. It would also store the SFTP password unencrypted, leave the dependencies unregistered and record no version history. A wrong row would only show up at month end, as a failed or missing file. The function goes through the same path as the screen, so a bad row is refused at once, with a reason.

2b · The ready-to-run script (2026-10-22)

scripts/sql/feeds_from_shared_query.sql wraps the call below for feeds on ONE shared query (an SQL file).

  1. Edit two blocks with names, never IDs:
    • the settings: template, SQL file, connections, SFTP, schedule, SLA, dependencies;
    • the entity list: VALUES rows, or a SELECT from your own table.
  2. Run the whole file in any PostgreSQL client: psql, DBeaver or pgAdmin.

The script:

  • checks every name first, and stops with the reason if one does not exist;
  • runs with dry_run = true to preview; set it to false to apply;
  • prints the result: created, updated, unchanged and refused, with the reason for each refusal.

The request state goes pending → running → done (or failed).

Proven on the Docker rig, scripts/docker_proof/feeds_from_sql_script_proof.py, 14/14. The script was run with psql. The dry run wrote nothing. A misspelt name stopped it with the reason. The real run created 3 feeds, each reading the shared SQL file, with the SFTP password encrypted. One feed ran and delivered to SFTP exactly the 5 rows Trino returns for its entity, with the token filled. Running the script again left every feed unchanged.

3 · Step by step

Step 1 — try it without writing anything (p_dry_run => true). The status view says how many feeds would be created, changed or refused, and why.

SELECT qs_feed_template_apply(
  p_template     => 'FACT_TETB_MONTH_END',
  p_parameters   => '["SYSTEM_ENTITY","EventCode"]',
  p_feed         => '{
      "name": "FACT_TETB_{SYSTEM_ENTITY}_{EventCode}",
      "description": "Month end, both sides of the shared fact_tetb query",
      "source_type": "sql_file", "source_id": 19, "connection_id": 613,
      "output_format": "csv",
      "output_filename_template": "fact_tetb_{SYSTEM_ENTITY}_{EventCode}_{business_date:YYYYMMDD}_{run_date:YYYYMMDD}.csv",
      "destination_type": "sftp",
      "destination_config": {"host": "sftp.example", "port": 22, "remote_dir": "/inbox",
                             "username": "feeduser", "password": "the SFTP password",
                             "host_key_b64": "AAAA..."},
      "schedule_declaration": {"kind": "month_end"},
      "sla_to": "18:00", "sla_timezone": "Europe/London"}',
  p_dependencies => '[
      {"dependency_type": "ORACLE_TABLE",
       "dependency_key": "finance_sl_balance_{SYSTEM_ENTITY}_{EventCode}_CLOUD",
       "arrival_sources": [{"kind": "kafka", "topic": "qs.kafka.message"},
                           {"kind": "oracle_table", "connection_id": 3, "table": "QS_KAFKA_MESSAGE"}],
       "require_mode": "any"},
      {"dependency_type": "ORACLE_TABLE",
       "dependency_key": "finance_sl_balance_{SYSTEM_ENTITY}_{EventCode}_ONPREM",
       "arrival_sources": [{"kind": "kafka", "topic": "qs.kafka.message"},
                           {"kind": "oracle_table", "connection_id": 3, "table": "QS_KAFKA_MESSAGE"}],
       "require_mode": "any"}]',
  p_matrix       => (SELECT jsonb_agg(jsonb_build_object('SYSTEM_ENTITY', code, 'EventCode', event))
                       FROM my_entity_list),          -- any table or query you have
  p_dry_run      => true);

Step 2 — check the result:

SELECT request_id, state, created, updated, unchanged, conflicts, refused, error
  FROM qs_feed_template_apply_status ORDER BY request_id DESC LIMIT 5;

-- the reason for each refused row:
SELECT r ->> 'name', r ->> 'reason'
  FROM qs_feed_template_apply_status s, json_array_elements(s.report::json -> 'refused') r
 WHERE s.request_id = 42;

Step 3 — run the same call with p_dry_run => false (or leave it out). The second shared query (fact_tetb_ext) is a second template: same call, its own name, its own SQL file and its own dependency names.

Later — new entities. Call again with only the template name and the new full list. Feeds that already exist come back as "unchanged", and only new rows become feeds:

SELECT qs_feed_template_apply(p_template => 'FACT_TETB_MONTH_END',
  p_matrix => (SELECT jsonb_agg(jsonb_build_object('SYSTEM_ENTITY', code, 'EventCode', event)) FROM my_entity_list));

Change something for all of them (for example the SLA): pass p_feed again with the change. Every member is updated, and each change is recorded in that feed's version history.

Remove entities: pass the reduced list with p_retire_missing => true. Feeds no longer in the list are retired (switched off and kept in history), never deleted.

4 · What to know

TopicHow it works
NamesFeed names follow the same rule as the feed screen: upper case, and hyphens, spaces and dots become _. Entity SAP-2920-EMEA gives FACT_TETB_SAP_2920_EMEA_EOD. Dependency names and file names keep the entity exactly as written, so they match the upstream messages.
PasswordsStored encrypted in every table: the feed, the template, its version history, and the request row (encrypted when QueryStudio picks it up, within about 10 seconds). Nobody reading the database sees them.
Who may do thisAnyone who can run the function can change every feed, so grant EXECUTE ON FUNCTION qs_feed_template_apply only to the release or DBA role. The status view shows who asked (the database login, or p_requested_by).
SpeedMeasured on the test system: 200 feeds in 44 s; a check of 5,000 in 4 s. A real 5,000 takes roughly 2 minutes in the background. Large requests never block the screen.
If QueryStudio restarts mid-wayA request still "running" after 30 minutes is applied again. That is safe: feeds already made come back "unchanged".
Where the function comes fromQueryStudio creates qs_feed_template_apply and qs_feed_template_apply_status itself in its own PostgreSQL database, shortly after it starts. There is nothing to install.
