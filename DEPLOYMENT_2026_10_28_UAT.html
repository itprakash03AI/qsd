Release b012dcc99, tag release/2026-10-28-b012dcc99. Two bundles are on qsd, built from the same commit:

  • Deployment_2026_10_28_b012dcc99.zip — changes only since Deployment_2026_10_22_9572643d8, the release UAT runs now. Use it if UAT already runs 9572643d8.

Each zip has a MANIFEST.txt naming the commit and every file. The changes-only zip also has a DELETED.txt listing files to remove. Zips over 24 MB are split into parts; the .PARTS.txt file next to them says how to join them. 1 · Before you start: what only your UAT can supply

Nothing new since the 2026-10-27 guide. The UAT values file k8s/querystudioapi-helm/env/uat.yaml holds what QueryStudio knows about UAT; the values only you can give are marked __SET_PER_ENV__, and the charts refuse to render while any marker is left.

  1. Copy env/example.site.yaml to env/uat.site.yaml (ignored by git, never commit it) and fill in UAT's own AD server, domain, service account and the three UAT groups (admins, analysts, viewers).
  2. The master key: the same value from Vault into all five deployments (api, scheduler, executor, reports, published-api) as QUERY_STUDIO_SECRET_KEY. For an existing UAT it must be the key UAT has always used. 
    oc create secret generic qs-master-key --from-literal=QUERY_STUDIO_SECRET_KEY="$KEY_FROM_VAULT"
for d in <api> <scheduler> <executor> <reports> <published-api>; do
  oc set env deploy/$d --from=secret/qs-master-key
done
  3. The environment name stays uat in uat.yaml.
  4. Spark pods only if UAT users will use them: spark_k8s.enabled, callback_base_url and feed_generation.webhook_secret in uat.site.yaml, as in the 10-27 guide.

2 · Install or upgrade

A new UAT

  1. Unzip Deployment_2026_10_28_b012dcc99_FULL.zip.
  2. Build the images: backend/ → the API image (also scheduler, executor, reports, published API); frontend/ → the UI image; spark/ → the Spark job image, only if you use Spark pods.
  3. Create the empty PostgreSQL database named in uat.yaml. QueryStudio creates every table itself on first start, including qs_kafka_message. There is no SQL script to run.
  4. cd k8s/querystudioapi-helm && ./deploy.sh uat.

An existing UAT on 9572643d8

  1. Unzip Deployment_2026_10_28_b012dcc99.zip over the source tree you built 9572643d8 from.
  2. Delete the paths listed in DELETED.txt.
  3. Rebuild the API image: it has one new Python package, defusedxml==0.7.1 (already in backend/requirements.txt; it lets the Excel upload read files safely). Rebuild the UI image too. Then ./deploy.sh uat.
  4. Database: new tables and columns are added on the first start; no existing column changes type. Since 9572643d8 that is the 8 tables of the 10-27 release plus qs_kafka_message.

3 · Check it is up (10 minutes, before users arrive)

  1. python scripts/verify_prod_config.py --profile uat --base-url https://<UAT API> --site-file k8s/querystudioapi-helm/env/uat.site.yaml (read only).
  2. No pod log says WAITING for the key, MASTER KEY MISMATCH or __SET_PER_ENV__.
  3. Sign in as an admin, an analyst and a viewer: each sees what their group allows.
  4. Admin → Monitoring → Component Health: every pod and connection green.
  5. The table: SELECT count(*) FROM qs_kafka_message; answers 0 (the table exists).
  6. One feed: Run Now on a small feed; it delivers and shows each step with a time.

4 · Your Kafka service writes into qs_kafka_message

Your existing Kafka service inserts one row per upstream message straight into QueryStudio's PostgreSQL. QueryStudio runs no Kafka consumer for it and needs no Oracle connection. The columns are the OG QS_KAFKA_MESSAGE columns (PostgreSQL shows them in lower case; "order" must be quoted, as in Oracle):

INSERT INTO qs_kafka_message (data_store, data_source, source_system_name, source_system_instance,
  business_date, code, business_event, cloud_compliant, "order", snap_version, version_number,
  version, catalogue_registration_time, version_state, row_count, processed)
VALUES ('QS', 'GB01', 'WS_STORE', 'uat', DATE '2026-10-31', 'SAP-2504', 'EOM', 'false', 'NA',
  '1', '1', 1, '2026-10-31T05:00:00', 'COMPLETE', 125000, 'N');

What QueryStudio does with a row. The QueryStudio worker on the scheduler pod reads new rows every 15 seconds and never changes them. A row releases the feeds waiting on the dependency named the OG way, <DATA_SOURCE>_<CODE>_<BUSINESS_EVENT>_<CLOUD|ONPREM> (cloud_compliant true → CLOUD, false → ONPREM), for that business date. Only version_state = COMPLETE releases a feed, and the feed's rows are checked against row_count. A row nothing waits for is kept and shown as not matched in Feeds → Dependency Messages. Nothing to configure in UAT: this is the default.

The database user your Kafka service uses needs only INSERT (and USAGE on the id sequence) on this one table.

One change to check before you upgrade: Admin → AWS Portal values only count when Enabled is on

The portal address, proxy, role and account set on Admin → AWS Portal are now used only while that page's Enabled switch is on. Before, they leaked into every AWS connection even with Enabled off. That broke connections that had their own settings, which is what happened on UAT. A connection that has its own portal settings is not affected. A connection that left those fields empty and relied on the Admin page now needs Enabled switched on there. The SSL check and the time-out always follow the Admin page.

Users asked for their password on an S3 connection

If a connection was saved with one person's own login, everyone else is asked for theirs. For a connection everyone should use through a Vault system account, an admin opens the connection and sets Credential source = System account. Then no user is asked for a password.
